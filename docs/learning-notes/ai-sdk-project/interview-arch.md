# Q1：告别面条代码：多态架构（Polymorphism）
> **面试官**：我看你的项目里接入了 DeepSeek、GLM 还有本地的 Ollama。如果我现在要求你新接一个 Kimi 大模型，你需要改动多少底层调度代码？如果在很多地方写 `if(model == "kimi") { ... } else if (...)` 会带来什么问题？你是怎么解决的？

![告别if-else，多态插座](file:///C:/Users/w1521/.gemini/antigravity/brain/8b0fcc1f-c673-43ec-b7cc-9311a41c4355/interview_04_polymorphism_1782355103432.png)

## 满分回答与机理拆解
如果大量使用 `if-else`，代码就会变成一坨无法维护的面条（Spaghetti Code），这严重违反了设计模式中的**开闭原则（Open-Closed Principle，对扩展开放，对修改封闭）**。
1. **多态的插座理论**：为了解决这个问题，我们在项目中抽象出了一个纯虚基类 `LLMProvider`。它就像一个标准的三孔插座，规定了 `Init`、`SendMessage` 等纯虚函数。无论你是 DeepSeek 还是 Kimi，只要你继承了这个类，实现了这些接口，你就是一个合格的“插头”。
2. **底层调度的零感知**：在 `LLMManager`（管家）中，我们只保存了基类指针 `std::map<std::string, std::unique_ptr<LLMProvider>>`。管家不需要知道它手底下的干活实体具体是谁，它只管调 `it->second->SendMessage()`。由于 C++ 虚函数表的**动态绑定（Dynamic Binding）**机制，指令会自动下发到正确的模型实例中执行。
3. **扩展代价极低**：接入 Kimi，我只需要新建一个 `KimiProvider.cpp` 继承基类，然后在 `ChatSDK` 初始化时注册进去即可，**完全不需要修改任何管家层面的代码**。

# Q2：化繁为简的艺术：外观模式（Facade Pattern）
> **面试官**：你的项目底层涉及了 SQLite 数据库、多线程并发锁、网络 `httplib`，极其复杂。但前端或者界面工程师在调用你的 SDK 时，却非常简单。请问你是如何进行架构分层与封装的？

![高层前台与底层管道](file:///C:/Users/w1521/.gemini/antigravity/brain/8b0fcc1f-c673-43ec-b7cc-9311a41c4355/interview_05_facade_1782355115537.png)

## 满分回答与机理拆解
这正是我们在 `ChatSDK.cpp` 中使用的**外观模式（Facade Pattern）**的魅力。
1. **为什么要用外观模式**：在企业级开发中，模块之间的耦合是大忌。如果前端 UI 代码直接包含了数据库操作的头文件，一旦底层数据库从 SQLite 换成 MySQL，整个 UI 层都要跟着重写。
2. **机理分层**：
   - **底层兵荒马乱**：`LLMManager` 负责复杂的网络路由；`SessionManager` 负责死磕各种 `NoLock` 免锁机制和原子操作；`DataManager` 负责拼写各种预编译防注入 SQL 语句。
   - **高层岁月静好**：在最顶层的 `ChatSDK` 类中，它就像五星级酒店的大堂前台。它左手拉着网络管家，右手拉着数据管家。它暴露出来的接口甚至连一个指针都没有，全是极其干净的 `std::string` 和基础数据结构。
3. **工作流闭环**：当外部调用 `SendMessageStream` 时，前台（ChatSDK）会自动指挥数据管家先存历史，再指挥网络管家发包，最后把结果封装好送回给外界。外界根本不知道里面到底经历了多少道工序。

# Q3：大模型流式截断机理（SSE vs JSON单换行）
> **面试官**：你讲到了流式传输。能说说大模型的流式数据在底层网络协议里长什么样吗？DeepSeek 的标准 SSE 协议和本地 Ollama 协议有什么本质区别？你的底层是怎么完成拆包断句的？

![传送带上的双换行定界](file:///C:/Users/w1521/.gemini/antigravity/brain/8b0fcc1f-c673-43ec-b7cc-9311a41c4355/interview_06_sse_1782355129861.png)

## 满分回答与机理拆解
这是整个项目中在网络层最折磨人、也是最具含金量的地方。
1. **标准 SSE 协议的机理**：DeepSeek 和 GLM 等云端模型遵循的是 Server-Sent Events (SSE) 协议。
   - **定界符**：每个数据包以 `data: ` 开头，以**两个连续的换行符（`\n\n`）**作为结束边界。
   - **终章信号**：当遇到 `data: [DONE]` 时，说明整个长篇大论全部输出完毕。
2. **Ollama 颠覆性的单换行协议**：Ollama 完全抛弃了 SSE！
   - 它没有任何前缀。它的每一个数据块就是一个**完整独立的 JSON 字符串**。
   - **定界符**：它仅仅依靠**一个换行符（`\n`）**来隔开两个 JSON 对象。
   - **终章信号**：它在每一个 JSON 对象里都会塞一个布尔值，只有当解析出 `root["done"].asBool() == true` 时，才宣告结束。
3. **手工打造拆包器**：
   由于网络底层 TCP 协议存在“粘包/半包”问题（网卡可能一次发来半段 JSON，也可能一次发来三段连着的 JSON）。我们在 `httplib` 的 `content_receiver` 回调中，建立了一个**内存暂存池（`std::string buff`）**。
   所有碎片数据先疯狂压入 `buff`，然后我们写了一个 `while` 循环，死磕在 `buff` 里寻找定界符（双换行或单换行）。找到了，就利用 `substr` 精确切出这段完整文本当作一个有效块，并立刻用 `erase` 把它从池子里销毁，以此实现了完美、零丢失的流式平滑拆包！
