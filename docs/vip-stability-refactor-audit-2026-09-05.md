# BottleMusic：VIP、卡死与重构审计（2026-09-05）

这次排查最重要的结论是：**会员领取、账号权益、歌曲鉴权、媒体完整播放是四个不同的验收点。历史上确实存在权益有效而歌曲仍是试听的情况。当前工程又存在可证实的稳定性隐患，不能把这些问题统称为“重构太多”，也不能用测试总数证明播放器已恢复。**

本次审计基于 HEAD `fd04497468554a66b95a69fdc693e32f2ceb68c9`、进入任务时已有的 18 个未提交 Native 文件，以及本机应用日志。用户记忆是“6 月以前大概正常，8 月下旬修复后可以试听”，不是可以直接用于二分的精确版本。本次保留原有业务代码，另写独立验证程序和报告。

### 1.2 当前显示逻辑不够可信：已离线复现

1. `ui/src/features/account/userStore.ts`：领取成功后先写 `isVip=true`；`syncVipAfterClaimSuccess()` 调用 `applyVipSnapshot(..., {allowDowngrade:false})`。即使权威会员查询明确返回无权益，仍保留 true，显示“权益状态同步中”。这条路径没有自动重查直到确认的闭环，只能等待其他显式刷新。
2. `vipResolver.ts`：顶层 `is_vip=1` 或 `vip_type>0` 可以在到期时间已经过去时仍返回 `isVip=true`；无法解析的到期日期也按永久/最高优先处理。
3. 现有 `userStore.test.ts` 明确断言“查询无权益时保留 optimistic VIP”。这说明问题不只是缺测试，还包括**测试保护了不适合作为业务事实的状态**。

此外，主领取按钮默认最多 8 轮、轮间 30 秒，成功也继续上报，单是间隔就最多 210 秒。它是异步等待，不等于 Windows 主线程卡死，但会让“领取一直转圈”的感受与真实卡死混淆；应单独显示当前阶段和可取消状态。

复现执行实际 TypeScript 源码，账号网络依赖使用固定响应。结果见 `outputs/vip-stability-audit-2026-09-05/frontend-probe-results.json`。它证明本地逻辑问题，不证明某次线上会员查询结果必然错误。

正确的最小调整方向：将“领取请求已接受”“权益待确认”“权益有效/已过期/未知”分开；待确认使用有上限的查询，不提前把它写成已确认 VIP；无效日期不能推定为永久会员。

### 1.3 歌曲链路中的具体问题

- `SongUrlService.cpp` 的 `BuildSongUrlOutput()` 将“非空 URL”映射为 `status=1`，试听也属于这种成功。前端可以播放试听是合理的降级，但必须与完整播放验收区分。
- v6 的试听判定依赖 URL 中是否有 `/full/`。未知 URL 结构不能单凭这个字符串证明是完整歌曲或试听。
- `Resolve()` 在选定其他音质 URL 后，没有同步重算该音质的 `is_preview` 等元数据。前端 `playbackOrchestrator.ts` 又做了一次选音质，进一步增加 URL 与标志错配的机会。
- v5 回退会覆盖原始上游响应。最终试听结果可能丢掉最初的鉴权拒绝原因；诊断应该保留各次尝试的状态、端点、音质和是否匿名，而不是只保留最后一次结果。
- Settings 的设备测试使用一首标注为免费歌曲的地址，并把 `/full/` 解释为“信任该指纹”。免费歌曲可播放不能证明 VIP 歌曲的完整播放权限。

完整播放应由每个音质对应的权利/片段信息，加上真实媒体时长、超过试听边界后的播放与接近结尾的 seek 来验收。`status=1`、URL 路径和数据库中的 `completed` 单个字段都不足以替代这个验收。

## 2. 卡死：高优先级证据与风险

### 2.1 本机确实出现过 Native 栈损坏

日志原文：

```text
2026-07-31 18:07:00.002: Run-Time Check Failure #2 - Stack around the variable 'ctx' was corrupted.
2026-09-04 12:04:29.736: Run-Time Check Failure #2 - Stack around the variable 'session' was corrupted.
```

位置分别为 `bottlemusic-20260731.log:644`、`bottlemusic-20260904.log:73`（下一行再次记录）。这属于内存安全/二进制一致性排查范围，优先级高于目录整洁和视觉调整。

**尚不能确定**是哪个函数写坏了栈、是否有旧对象/库与新头文件混用，或与另一台 Windows 的卡死是否同源。只有变量名，没有调用栈和 dump，不能定位越界写入者。也不能仅依据历史 CHANGELOG 就把原因判为 MSVC 增量链接。

下一步需要在可复现构建中保留 PDB、捕获首次异常与线程栈，并使用 ASan 或相应运行时检查定位首个非法访问。独立干净构建用于排除部分旧产物因素，不能证明线上长期运行没有内存问题。

### 2.2 WinHTTP 超时取消违反同步句柄使用要求：P0

`native/core/HttpClient.cpp` 使用 `WinHttpOpen(..., 0)` 创建同步 session；`ArmRequestHandleWatchdog()` 则让另一个 watchdog 线程执行 `WinHttpCloseHandle(request)`，意图中断正在 `WinHttpSendRequest` / `ReceiveResponse` / 读数据中的同步调用。

微软规定：同步请求的句柄只能在没有线程正在使用并等待该句柄的 WinHTTP 调用返回时关闭（特定回调情形除外）。而这里正是为了取消尚未返回的调用。CAS 防止两次 Close，不等于解决 Close 与正在使用句柄的竞争；句柄关闭后也可能被 WinHTTP 重用。[微软 WinHTTP 并发要求](https://learn.microsoft.com/en-us/windows/win32/winhttp/concurrency-in-winhttp)

这条实现风险已经由代码和官方契约确认；**它是否就是用户那次卡死的触发点仍未证明**。修复应采用合规的请求所有权和取消模型，例如异步 WinHTTP 请求的回调生命周期；不能只加一把锁阻塞超时线程，或再包一层计时器。

### 2.3 统计命令会同步阻塞主线程：P1

`ui/src-tauri/src/stats.rs` 的 6 个 Tauri command 都是同步 `pub fn`，直接调用 C++ 统计入口。后者会取锁并通过 Storage Actor 的 `future.get()` 等待数据库。

Tauri 文档说明，未声明 async、也未使用 `#[tauri::command(async)]` 的命令在主线程执行。遇到磁盘慢、数据库等待或锁竞争，这条链路可阻塞窗口；数据库放到独立线程并没有让同步等待它的调用者自动变成异步。[Tauri 命令线程说明](https://v2.tauri.app/develop/calling-rust/#async-commands)

应将统计 FFI 等待迁出 UI 主线程，并为排队、超时和关闭定义完整边界；仅给函数加 `async`，但继续在异步执行器上做阻塞 FFI，也不充分。

### 2.4 “超时”“并发上限”“停止工作”仍被混用

- `lib.rs` 的 16 个 semaphore permit 在调用者超时后立即归还，而 `spawn_blocking` 的工作继续运行。所以 16 只是当前尚未超时的准入上限，不是存活 FFI 工作的硬上限。现有测试也明确保护立即归还的行为。[Tokio spawn_blocking 取消语义](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)
- `RequestWatchdog.cpp` 用一个线程串行执行所有超时 action，调度器 deadline 与 WinHTTP 关闭动作共享这个线程。如果一个 action 阻塞，其他 deadline 也会延迟；需要把纯计时通知与可能阻塞的资源回收分离。
- C++ 有 4 个 worker 和队列上限，正常情况下确实能限制工作；这有价值。但“future 超时返回”不等于底层线程已回收，更不能单凭这个设计宣称绝不会卡死。

独立干净构建中的三个离线探针进一步确认：

1. 挂起一个 watchdog action 后，另一个 30ms deadline 在 150ms 后仍未兑现；解除前者后才出现 `job_deadline`。这是共享计时线程的相互影响复现，并未声称真实 WinHTTP Close 已在本机永久阻塞。
2. 同一曲目提供高音质完整 URL 和低音质片段 URL，选择低音质后返回了片段地址，却保留 `is_preview=false`。
3. `SubmitWithDeadline` 的非 void 任务抛出服务异常时，内部 `catch (...) {}` 吞掉原异常，最终暴露 `broken promise`，不是原来的服务错误。这会降低诊断质量；它不是本次卡死的已证实根因。

结果保存在 `outputs/vip-stability-audit-2026-09-05/native-probe-results.json`。

缺少故障机器的日志、Windows/WebView2 版本和 hang dump，本次不将上述风险强行归因为那一次故障。既有长时间 soak 报告也明确写着 2h/24h 未执行。

## 4. 下一阶段按这个顺序执行

1. **稳定性 P0**：保留当前代码快照与精确 DLL/PDB；修 WinHTTP 合规取消；针对栈损坏捕获首次异常。把统计 FFI 从窗口主线程迁出。
2. **会员业务 P0**：修正“领取已受理 / 权益有效 / 歌曲完整播放”的状态定义。使用一首免费对照曲和至少两首确认需要会员且账号确有对应权益的歌曲，核验旧会话恢复与新登录两条路径；输出脱敏端点状态和选定音质。
3. **完成播放验收**：实际越过试听边界，seek 到接近歌曲结尾，核对媒体实际时长；登录/领取成功不替代这一项。不要只依赖 URL 中的 `/full/` 或固定 60 秒阈值。
4. **防回归**：录制脱敏真实响应作为夹具，覆盖过期、鉴权拒绝、试听、完整流、混合音质、失败后原始原因保存；在故障机做断网恢复、切歌、统计、关闭测试，再做有真实播放的长时间运行。
5. **最后再整理**：只做有助于以上工作的小范围结构调整，暂不重写三层架构。
