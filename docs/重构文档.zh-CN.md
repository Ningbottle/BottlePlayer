# BottleMusic 下一阶段重构计划书

本文回答「接下来怎么重构」。项目身份、酷狗音乐概念版参数、设备指纹、VIP 与播放事实只以 `docs/PROJECT_LOGIC.zh-CN.md` 为准。

本文不重复 API 事实，不重新定义酷狗概念版参数；只沉淀工程结构、风险、优先级、任务切片和验收方式。

## 1. 当前架构基线

BottleMusic 当前运行链路：

```text
Vue 3 UI
  └─ ui/src/api/backend.ts
      └─ HTTP loopback 127.0.0.1:6609
          └─ EchoCompatServer.exe
              ├─ CompatServer       socket/http 兼容层
              ├─ CompatApi          兼容 route 分发
              ├─ EchoCore           酷狗接口、签名、DTO、错误模型
              ├─ EchoStorage        SQLite、登录态、设备信息、设置
              ├─ EchoPlayback       播放状态机
              ├─ EchoImage          图片解码与缓存
              ├─ EchoAsync          后台任务
              └─ EchoDiagnostics    日志、脱敏、内存快照、耗时工具
```

主要约束：

- UI 使用 Tauri 2 + Vue 3 + Vanilla CSS。
- 前端业务请求统一经 `ui/src/api/backend.ts`。
- UI 线程不做网络、SQLite、图片解码、Media Foundation。
- 酷狗细节集中在 EchoCore。
- `dfid`、`mid`、`uuid`、`guid`、`mac`、`token` 不泄漏到 UI。
- 大响应不长期保留原始 JSON。
- 不新增大依赖，不引入无上限缓存。

## 3. 当前剩余问题

### 3.1 `CompatApi` 仍是浅 Module

`native/core/CompatApi.cpp` 仍承担太多职责：

- route 分发；
- query/body 解析；
- session/device 加载；
- Service 组装；
- fallback payload；
- 登录成功后的设备注册副作用；
- VIP/profile 合并；
- 部分 route-level 日志。

问题：

```text
Interface 看似只有 Handle(method, path, query, headers, body)
Implementation 却包含大量业务规则和存储细节。
```

这导致：

- 修改登录态规则需要搜索多个 route。
- 修改设备准备规则需要进入多个 route。
- 测试常常只能测大 route 行为，定位差。
- 新 agent 进入时认知成本高。

### 3.2 `CompatRequestContext` 覆盖面不足

目前只有 `/song/url` 使用 `CompatRequestContext`。

仍直接读取 session/device 的 routes 包括：

- `/register/dev`
- `/playlist/track/all`
- `/playlist/track/all/new`
- `/user/history`
- `/playlist/add`
- `/playlist/del`
- `/playlist/tracks/add`
- `/playlist/tracks/del`
- `/user/detail`
- `/user/vip/detail`
- `/youth/listen/song`
- `/youth/vip/ad`
- `/user/playlist`
- 登录成功后的设备注册分支

### 3.3 还没有真正的 `RequestScheduler`

已经完成的是 latest-wins tracer bullet，不是完整 Scheduler。

仍存在：

- `BackendFacade` 多处 `std::async(std::launch::async)`。
- `MainWindow` 仍有若干 `std::async`。
- `CompatServer` 单线程同步处理请求。
- search、playlist、login polling、image loading 没有统一并发上限。

### 3.4 `CompatServer` 是同步单请求处理

当前 `CompatServer` accept 一个 client 后同步：

```text
recv -> ParseRequest -> api.Handle -> SendResponse -> close
```

影响：

- 一个慢 `/song/url` 会阻塞后续 HTTP 请求。
- 前端 abort 不能真正中断后端已进入的同步 route。
- `/diagnostics/memory` 等轻请求也可能排队。

### 3.5 UI 请求状态仍有若干 stale 风险

已修复播放 URL 的 stale 写入，但仍有：

- `LoginView` QR polling 可能重入。
- `userStore.checkLoginStatus` 多次调用时可能互相覆盖。
- `/register/dev` 是 fire-and-forget，UI 只能从 console 看到失败。
- `SearchView`、`PlaylistView` 翻页/切换没有 latest-wins。

### 3.6 测试缺口

已有 tests 覆盖大量 contract 行为，但仍缺：

- `CompatApi /song/url` latest-wins 行为。
- `BackendFacade::ResolveSongUrl` stale generation 行为。
- UI `playTrack` 快速切歌只最后一次写 `audio.src`。
- `LoginView` polling 防重入。
- `CompatServer` header 大小写和畸形 `Content-Length`。

## 4. 下一阶段目标

下一阶段不要继续堆零散 helper。目标是把当前浅 Module 变深：

```text
CompatApi 从 “巨型 route switch”
变成
route 分发 + RequestContext + 分组 Route Module + Scheduler + Diagnostics
```

关键 Module：

| Module | 目标 |
| --- | --- |
| `CompatRequestContext` | 集中 session/device/query/body/request metadata |
| `CompatRouteHandlers` | 按领域拆 route 行为，缩短 `HandleKnownRoute` |
| `RequestScheduler` | bounded queue、latest-wins、取消 token、耗时日志 |
| `CompatServerRuntime` | 管理 socket client 的请求提交和响应发送 |
| `RequestDiagnostics` | route、status、elapsed_ms、canceled、error_code 结构化日志 |

## 5. 优先级路线图

### P0：低风险稳定性补丁

状态：基本完成。

已完成：

- 脱敏真实 `dfid` 日志。
- 删除调试遗留注释。
- header key 小写化。
- `Content-Length` 异常保护。

后续只在发现明确 bug 时补。

### P1：UI 请求体感补丁

目标：

- 防止登录状态和 QR polling 的旧请求污染状态。
- 减少重复请求造成的卡顿。

任务：

1. `LoginView` QR polling 防重入。
   - 增加 `pollingInFlight`。
   - 上一次 `/login/qr/check` 未结束时跳过下一轮。
   - 组件卸载时停止 polling。

2. `userStore.checkLoginStatus` 加 request id。
   - 多次调用只允许最后一次写 `userStore`。
   - `detail`、`vip`、`register/dev` 的错误分别归因。

3. `/register/dev` 状态显式化。
   - 不只 console.warn。
   - 可以在 Settings 或 userStore 中展示“设备注册中/失败/已注册”。

验收：

- 登录页连续刷新二维码不会并发堆积 polling。
- 多次触发 `checkLoginStatus` 不会回滚 UI。
- 设备注册失败有可见状态或稳定错误归因。

### P2：扩展 `CompatRequestContext`

目标：

- route 不再直接知道 `SessionRepository` / `DeviceRepository`。
- session/device 加载规则集中。

迁移顺序：

1. `/user/detail`
2. `/user/vip/detail`
3. `/user/playlist`
4. `/playlist/add`
5. `/playlist/del`
6. `/playlist/tracks/add`
7. `/playlist/tracks/del`
8. `/youth/listen/song`
9. `/youth/vip/ad`
10. `/register/dev`

建议扩展 Interface：

```cpp
class CompatRequestContext {
 public:
  const std::optional<SessionInfo>& Session();
  std::string UserIdOr(std::string_view fallback);
  std::string TokenOrEmpty();
  bool HasLogin();
  const DeviceInfo& Device();
};
```

注意：

- 不要让 `CompatRequestContext` 变成万能上帝对象。
- 它只负责 request-scoped state，不负责调用酷狗 upstream。
- route handler 仍负责业务语义。

验收：

- `CompatApi.cpp` 中直接出现 `SessionRepository` / `DeviceRepository` 的次数显著下降。
- 每迁移一组 route，保留或新增 contract tests。

### P3：拆分 `CompatApi` route Module

目标：

- 提升 Locality：用户、歌单、播放、VIP、登录各自成块。
- `CompatApi::HandleKnownRoute` 只做 route 分发。

建议拆分：

```text
native/core/compat_routes/
  UserRoutes.cpp
  PlaylistRoutes.cpp
  SongRoutes.cpp
  LoginRoutes.cpp
  YouthVipRoutes.cpp
  DiagnosticsRoutes.cpp
```

每组 Module 的 Interface 应小：

```cpp
CompatResponse HandleUserDetail(CompatRequestContext& ctx, const QueryMap& query);
CompatResponse HandleUserVip(CompatRequestContext& ctx, const QueryMap& query);
```

不要一开始抽象过度：

- 先迁移现有逻辑；
- 不改变 response shape；
- 不改变酷狗参数；
- 不新增大依赖。

验收：

- `CompatApi.cpp` 行数明显下降。
- route 行为测试不需要读巨型 switch。
- 每个领域 route 能独立 review。

### P4：真正的 `RequestScheduler`

目标：

- 替代无界 `std::async(std::launch::async)`。
- 对高频请求做 bounded concurrency。
- 支持 latest-wins 和 cancellation token。

建议 Interface：

```cpp
enum class RequestKind {
  SongUrl,
  Search,
  Playlist,
  LoginPoll,
  Image,
  Generic,
};

class CancellationToken {
 public:
  bool IsCancellationRequested() const;
};

class RequestScheduler {
 public:
  template <class Fn>
  auto Submit(RequestKind kind, Fn fn);

  template <class Fn>
  auto SubmitLatest(RequestKind kind, Fn fn);

  void Cancel(RequestKind kind);
};
```

实现要求：

- bounded queue；
- 固定 worker 数；
- 拒绝或丢弃策略稳定；
- request id / generation 不悬空；
- 日志包含 queue_wait_ms、run_ms、canceled。

第一批接入：

1. `BackendFacade::ResolveSongUrl`
2. `CompatApi /song/url`
3. `/search`
4. `/playlist/track/all`
5. QR polling

验收：

- 快速提交 10 个 `/song/url`，只最后一个写状态。
- worker 数不随请求数线性增长。
- stale request 返回稳定 canceled。
- smoke tests 通过。

### P5：`CompatServerRuntime`

目标：

- 解决 `CompatServer` 单线程同步处理导致的阻塞。
- 不要每个 client 一个无界线程。

建议：

```text
accept thread
  └─ parse request
      └─ submit to RequestScheduler
          └─ route handler
              └─ send response
```

注意：

- socket 生命周期必须明确。
- response 发送失败不能崩溃 server。
- OPTIONS 和 `/diagnostics/memory` 可走快速路径。
- 不要把业务逻辑搬进 `CompatServer`。

验收：

- 一个慢 `/song/url` 不阻塞 `/health` 或 `/diagnostics/memory`。
- 并发请求不会创建无界线程。

### P6：Diagnostics 降噪与结构化

目标：

- 日志从“哪里都打一行”变成 route-level 摘要。

建议：

- 删除高频低信息日志，例如每个 `JsonResponse` 的 entry/constructed。
- 新增 route summary：

```text
[CompatApi] route=/song/url status=1 elapsed_ms=352 canceled=N error_code=
[BackendFacade] op=ResolveSongUrl queue_wait_ms=2 run_ms=350 canceled=N
```

要求：

- 所有日志先 `RedactSensitive`。
- URL 最多 400 bytes。
- body 最多 800 bytes。
- 不打真实 token、dfid、Cookie、KugooID。

## 8. 执行规则

每个任务都必须：

1. 先确认 Module、Interface、Implementation、Seam。
2. 不改变酷狗音乐概念版 API 事实。
3. 不把标准版参数或 m 站 Cookie-only 路线写成默认事实。
4. 不新增大依赖。
5. 不引入无上限队列或缓存。
6. 不让 UI 线程做网络、SQLite、图片解码、底层播放调用。
7. 修改 native 后跑构建和 smoke tests。
8. 修改 UI 后跑类型检查。

## 10. 一句话结论

本轮 A-E 已完成了「可观测性、重复工具提取、局部 RequestContext、数据库生命周期、播放 URL latest-wins」这些 tracer bullets。

下一轮真正有 Leverage 的方向是：

```text
CompatApi 从巨型兼容路由实现，逐步变成
RequestContext + 分组 Route Module + RequestScheduler + 结构化 Diagnostics。
```
